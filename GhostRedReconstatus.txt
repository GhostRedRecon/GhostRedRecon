Executive Summary
=================

GhostRedRecon is not ready for a public v1 release yet.

The project has a substantial FastAPI backend, a React/Vite operator console, focused tests for WiFi/camera/drone evidence workflows, startup scripts, deployment notes, and a broad feature set. Several core workflows are implemented and some are validated by tests. However, the repo is not currently GitHub-ready or production-ready because:

- The current directory is not an initialized Git repository.
- Python source compilation fails in five backend modules.
- Backend Python dependencies are not declared in pyproject.toml or requirements files.
- The release tree contains runtime/generated artifacts: evidence captures, logs, SQLite DB, frontend dist, node_modules, pytest cache, and __pycache__ files.
- There is no README, LICENSE, security policy, contribution guide, release notes, or public-safe quickstart.
- Some features are hardware-dependent and cannot be called "working" without device/toolchain validation on the target host.
- Several backend routes can execute privileged or offensive-adjacent actions and need authorization, consent gates, and public-release safety documentation.

Features Not Working, Unproven, or Not Release-Ready
====================================================

Blocking code issues:
- Five backend/recon/detection modules are syntactically invalid. Even if they are not on the current import path, public v1 cannot ship with Python source that fails compileall.
- No backend dependency manifest exists. pyproject.toml contains only project name/version and pytest config, not install/runtime dependencies such as fastapi, uvicorn, numpy, pydantic, pytest, or hardware/tool integrations.
- pyproject.toml version is 0.1.0 while backend/main.py advertises API version 21.0.0 and frontend/package.json is 1.0.0. Release versioning is inconsistent.
- backend/main.py and runtime.py contain non-ASCII emoji-heavy banners and comments. Not a functional bug, but noisy for public package maintenance and logs.

Repository/GitHub readiness issues:
- Current folder is not a Git repository.
- No README was found.
- No LICENSE was found.
- No requirements.txt, uv.lock, poetry.lock, or backend dependency list was found.
- No SECURITY.md was found. This project needs one because it includes RF, WiFi, BLE, drone, replay, validation, and red-team-adjacent capabilities.
- No CONTRIBUTING.md, CODE_OF_CONDUCT.md, changelog, release checklist, or public v1 tag notes were found.
- Runtime data and caches are present in the workspace. They must not be published.
- frontend/node_modules and frontend/dist are present locally and should not be committed.
- ghostrecon_devices.db is present at repo root. It may contain local device data and should not ship publicly unless explicitly sanitized and documented.
- evidence/ contains many PCAP/PCAPNG/json artifacts and likely real-world identifiers. It must be removed from public release or replaced with a tiny sanitized sample dataset.

Operational/hardware concerns:
- HackRF SDR paths are implemented but require HackRF hardware and external commands such as hackrf_info and likely hackrf_transfer.
- WiFi MK7 paths require monitor-mode-capable WiFi adapters and privileged capabilities such as CAP_NET_ADMIN/CAP_NET_RAW.
- BLE NR5 paths require nRF52840/BLE tooling and may require OS-level Bluetooth permissions.
- Hunt Drones integrations mention DJI/OpenDroneID-style adapters. Actual radio/decoder operation was not hardware-validated in this audit.
- Startup scripts may stop existing port owners and write generated frontend config. That is practical locally, but public docs must warn users clearly.
- systemd unit paths point to /home/ghost/Documents/GhostRedRecon, while the audited project is /home/ghost/Documents/GhostRedRecon/GhostRedRecon. Deployment paths need normalization.

Security/public release concerns:
- CORS is configured as allow_origins=["*"] in backend/main.py. This is convenient for development but not production-safe.
- There is no authentication or authorization layer visible at the FastAPI app boundary.
- Backend routes expose privileged control actions including restart, SDR control, WiFi operations, BLE validation, evidence access, red-team validation, and replay-style workflows.
- Artifact download routes have path allowlist checks, which is good, but public release needs a broader threat model for local file exposure, sensitive evidence, and operator data.
- Offensive-adjacent workflows should be documented as authorized-lab-only, with explicit safety gates and defaults biased toward passive/defensive operation.

Testing gaps:
- Tests currently focus on WiFi/camera/drone evidence workflows. There are no broad endpoint tests for the full FastAPI surface.
- There is no frontend test suite.
- There is no lint/typecheck configuration.
- There is no CI configuration.
- There are no packaging/install tests from a clean checkout.
- No tests verify that all Python files compile. compileall currently fails.
- No tests verify that generated/public config is absent from a clean release tree.

Problems Found And Fixed
------------------------
- Full operator snapshots could hang for more than 10 seconds because include_data snapshots synchronously triggered heavy target artifact and handshake evidence generation through tshark. Fixed by using lightweight target snapshots during active capture and while artifact materialization is running.
- The staged processing pipeline was calling full target enrichment while scanning. Fixed by wiring it to lightweight network/client getters so live capture does not trigger retained-evidence artifact work.
- Scan completion synchronously materialized all target artifacts, blocking operator responsiveness. Fixed by moving artifact materialization to a background worker with status reporting.
- Single-adapter 60-second WiFi Hunt runs actually planned 105 seconds of wall-clock work: 20s airodump + 60s core capture + 15s Kismet + 10s Bettercap. Fixed the planner so the requested duration is the total wall-clock budget. A 60-second run now plans 10s airodump + 39s dumpcap/tshark + 6s Kismet + 5s Bettercap.
- No-handshake scans still spent memory and CPU extracting empty handshake PCAPs for each target. Fixed by skipping handshake extraction unless the tracker has observed EAPOL/authentication evidence for that target. Handshake artifacts are still produced when actual evidence exists.

--------------------

Camera Hunt Router Filter Fix - 2026-06-06
==========================================

Issue
-----
The Camera Hunt UI could show routers/APs in the camera list when no confirmed camera leads existed. Root cause: the frontend merged backend near_misses and heuristic fallback candidates into the primary cameraLeads list. The backend near-miss logic also treated vendor-family camera signatures as enough discriminator for near-miss visibility, so TP-Link/router-like APs could appear even without RTSP, ONVIF, IP, cloud, WPS-camera, stream, or scenario evidence.

Fix
---
- Backend near-miss gating now requires real camera discriminator evidence: RTSP/ONVIF/discovery-style protocol evidence, local/cloud camera vendor state, historical camera identity, explicit WPS camera class, or client camera/NVR role context.
- Router/hub/speaker winners are excluded from Camera Hunt near_misses unless that real camera discriminator exists.
- Frontend Camera Hunt primary camera list now uses retained backend leads only. Near-misses are no longer promoted into the main camera list when retained leads are empty.
- Frontend strong-candidate filtering now blocks infrastructure networks from camera-capable/likely paths unless protocol or explicit camera identity evidence exists.
