GhostRedRecon Project Audit
Generated: 2026-05-05

1. Executive Summary

GhostRedRecon is a large RF reconnaissance and operator-console repository built around a React/Vite frontend and a FastAPI backend. Its core product is a multi-tab SIGINT console for HackRF-based SDR work, native Wi-Fi capture, BLE assessment, passive drone hunting, retained evidence review, and operator guidance.

The application code is much smaller than the repository footprint suggests:
- Total files scanned excluding `frontend/node_modules`, `frontend/dist`, `backend/.venv`, and nested `.git`: 53,182
- Backend tracked files excluding `.venv` and `__pycache__`: 241
- Frontend source files in `frontend/src`: 38
- `scripts/` files: 2,767
- `tests/` + `test scripts/` files: 19
- `evidence/` size: 537 MB
- `backend/.venv` size: 156 MB
- `frontend/node_modules` size: 46 MB
- `gr-bluetooth` size: 113 MB

Practical conclusion:
- This repo is both an application and a data dump.
- Product code exists, but maintainability is being degraded by archived evidence, generated files, vendored code, and feature-registry drift.

2. High-Value Findings

2.1 Tab registry drift is a real product bug
- `frontend/src/App.jsx` hardcodes the visible navigation model.
- `frontend/src/lib/runtime.js` separately defines another tab registry.
- These two registries do not match.
- Evidence:
  - `frontend/src/App.jsx:60-70` defines primary tabs as `HOME`, `SDR-HKRF`, `BLE-NR5`, `HUNT-DRONES`, `WIFI-MK7`, `CAMERA-HUNT`, `REPORTS`, `SETTINGS`, `MANUAL`
  - `frontend/src/lib/runtime.js:10-28` defines a different default list including `SUB-GHZ`, `BLE`, `LORA`, `ZIGBEE`, `IOT`, `WIFI`, `WB-HUNT`, `CAMPAIGNS`, and no `SDR-HKRF` grouping
- Impact:
  - Configurable tabs are not the same thing as reachable tabs.
  - UI behavior can diverge from configuration.
  - Future tab additions/removals will break easily.

2.2 `CampaignsView` is implemented but effectively unreachable
- `frontend/src/App.jsx:1105-1106` renders `CampaignsView` when `activeTab === 'CAMPAIGNS'`.
- But `CAMPAIGNS` is not present in the primary tabs shown in `App.jsx`.
- It is also missing from `VALID_VIEW_TABS` in the visible App shell path.
- Result:
  - The feature exists in code and config, but is not exposed through the active UI.

2.3 The repository is overloaded with runtime artifacts
- `evidence/`, `rf_reports/`, `logs/`, `tools/`, and `scripts/evidence/` dominate the repository.
- This makes code review, onboarding, search, backup, sync, and version control worse.
- The repo is acting as:
  - source repository
  - evidence archive
  - runtime workspace
  - test lab
  - vendored dependency store

2.4 Test execution is not healthy by default
- Running `pytest -q tests/test_hunt_drones.py` fails at collection because `backend` is not on `PYTHONPATH`.
- Running `env PYTHONPATH=. pytest -q tests/test_hunt_drones.py` collects, but still fails:
  - `tests/test_hunt_drones.py:143` expects `first["live_lead_count"] == 1`
  - actual result was `0`
- Current state:
  - 13 tests passed
  - 1 test failed
  - plain `pytest` is not ready-to-run from a clean shell

2.5 Some source files look orphaned or at least unproven
- Strong frontend candidates:
  - `frontend/src/views/CategoryView.jsx`
  - `frontend/src/lib/categoryIntel.js`
- Strong backend candidates from repository-reference scan:
  - `backend/integrations/ble_pipeline.py`
  - `backend/recon/features/frame_structure_detector.py`
- These should be treated as "review candidates", not automatically deleted, because low reference count can still hide reflective or future use.

2.6 Legacy and vendored code is mixed into the active repo root
- `frontend/legacy/*` explicitly says it is reference-only and not the production UI.
- `gr-bluetooth/` appears vendored and is not visibly wired into the current frontend/backend product path.
- This is fine for a lab repo, but not for a maintainable product repo unless clearly separated.

4. Architecture

4.1 Runtime flow
- Entry point: `backend/main.py`
- Backend app: FastAPI
- Main orchestrator: `backend/runtime.py`
- Runtime design:
  - builds a singleton runtime
  - injects it into `app.state.runtime`
  - registers routers
  - tries to degrade safely if runtime init fails

Observed backend layers:
- `backend/api/`
  - HTTP surface for system, RF, intel, devices, integrations, Wi-Fi MK7, BLE-NR5, attack, hunt-drones
- `backend/runtime.py`
  - composition root and orchestration layer
- `backend/session/session_controller.py`
  - session lifecycle
- `backend/sdr/`, `backend/fft/`, `backend/analysis/`
  - SDR and signal processing
- `backend/intel/`
  - signal enrichment and device-oriented intelligence
- `backend/recon/`
  - deeper detection, fingerprinting, protocol, intelligence, and fusion logic
- `backend/integrations/`
  - Wi-Fi MK7, BLE-NR5, hunt-drones, `rtl_433`, wideband sweep, and related controllers

4.2 Frontend flow
- Entry point: `frontend/src/main.jsx`
- App shell: `frontend/src/App.jsx`
- Shared service layer: `frontend/src/lib/api.js`
- Runtime/config layer: `frontend/src/lib/runtime.js`
- Shared UI primitives:
  - `CategoryConsole.jsx`
  - `IntegrationWorkbench.jsx`
  - `HeroHeader.jsx`
  - `RealtimeTopologyRail.jsx`
  - `SignalTable.jsx`
  - `DeviceList.jsx`
  - `handheld.jsx`

4.3 Startup and deployment
- Main dev launcher: `scripts/start.sh`
- Stop script: `scripts/stop.sh`
- Config source: `config/project.config.json`
- Generated frontend runtime config: `frontend/public/config.js`
- Privileged backend deployment hint: `deploy/systemd/ghostredrecon-backend.service`

Important operational detail:
- `scripts/start.sh` writes `frontend/public/config.js` from `config/project.config.json`, then launches frontend/backend.
- `deploy/systemd/README.md` confirms `WIFI-MK7` may need `CAP_NET_ADMIN` and `CAP_NET_RAW`.

5. Design Principles Observed

These are visible in code and comments, not just inferred:
- Singleton runtime wiring
- Fail-safe startup and degraded operation
- Additive intelligence rather than replacing core signal truth
- Separation between shared SDR path and native platform tabs
- Evidence-first workflows for Wi-Fi, camera, BLE, and drone hunting
- Reusable UI primitives instead of fully bespoke tabs
- Operator-state persistence via local/session storage
- Red/Blue context switching in the same product shell
- Handheld-first alternative layout for field use

9. What Can Be Made Better

9.1 Architecture and product structure
- Create a single tab registry source of truth and drive both navigation and config from it.
- Separate source code from retained evidence and generated runtime outputs.
- Move vendored external projects like `gr-bluetooth/` into a dedicated third-party or submodule strategy.
- Split the repo into:
  - app code
  - host/runtime config
  - evidence/artifacts
  - optional research/vendor trees

9.2 Build and dependency hygiene
- Add a real backend dependency manifest:
  - `pyproject.toml`
  - or `requirements.txt`
- Do not rely on a committed `.venv` as the de facto dependency spec.
- Document the backend startup contract and expected host dependencies in one canonical README.

9.3 Testing
- Fix plain `pytest` discovery by making the backend importable without manual `PYTHONPATH=.`
- Investigate the current failing hunt-drones test
- Expand formal tests beyond the hunt-drones path
- Distinguish exploratory scripts from actual CI-grade tests

9.4 Product and UX
- Reconnect or remove `Campaigns`
- Decide whether `Signal Lab`, `Kismet Fusion`, and some workbench tabs are production features or placeholders
- Reduce the number of partially overlapping RF views if they are confusing operators
- Make live/offline/stateful workflows more explicit in the UI so operators know which tabs own hardware resources

9.5 Repo hygiene
- Create clear ignore/archive policies for:
  - `evidence/`
  - `logs/`
  - generated reports
  - pcaps
  - large binary blobs
- Move top-level one-off notes into `docs/` or `archive/`
- Keep only current operational docs in the repo root

10. Recommended Cleanup Order

1. Fix the tab registry split between `App.jsx`, `runtime.js`, and `config/project.config.json`
2. Decide the fate of `CampaignsView`
3. Add backend packaging/dependency metadata
4. Fix pytest importability and the failing hunt-drones test
5. Move runtime artifacts and retained evidence out of the product repo
6. Review orphan candidates and delete only after reference confirmation
7. Isolate or externalize `gr-bluetooth`

11. Bottom Line

GhostRedRecon is not a toy project. It has substantial product depth in Wi-Fi MK7, BLE-NR5, hunt-drones, shared SDR workflows, and evidence-backed operator tooling.

Its main weakness is not lack of capability. Its main weakness is repo discipline:
- duplicated UI configuration
- unreachable feature branches
- heavy artifact accumulation
- weak dependency/test packaging
- probable orphan code

If the repository is cleaned and the navigation/config/runtime contracts are unified, this can become much easier to maintain without losing the specialized field capability already built into it.
